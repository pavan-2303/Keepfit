# Version Spec - v0.11.0 - Reinstall-Safe Data Continuity

> **Linked initiative:** [Durable Personalized Fitness Companion](../backlog/items/durable-personalized-fitness-companion.md)
> **Status:** Approved and frozen for execution
> **Estimated effort:** 8-12d
> **Risk:** High
> **Prerequisites:** [v0.10.0 complete](../done/versions/v0.10.0.md)

---

## Sprint Goal

Protect Keepfit's structured fitness records and non-secret preferences across
supported Android reinstall and device-transfer flows without treating platform
backup as guaranteed or allowing credentials and private media into the backup.

## Delivered Increment

A user whose device and Android backup service support restoration can recover
the Room database and ordinary settings after reinstall. Transformation photos,
imported exercise media, OpenRouter credentials, pending authorization state,
and encrypted assistant drafts remain excluded. The existing encrypted manual
backup continues to be the explicit complete-data recovery path. A user may
separately opt into safe OpenRouter credential recovery when Block Store is
available, and every unavailable, missing, or invalid-token outcome falls back
to reconnecting.

## Work Items

### Item 1 - Allowlisted Android backup policy

**Why**

Android backup is currently disabled, so uninstall always removes structured
records even on devices that could restore them.

**What to do**

1. Enable Android backup and attach Android 12+ data-extraction rules plus the
   legacy full-backup rule file required by the platform contract.
2. Allowlist only `keepfit.db` and the non-secret
   `datastore/keepfit_settings.preferences_pb` file for cloud backup and
   device-to-device transfer.
3. Keep all ordinary files and shared preferences excluded by omission,
   including imported media, transformation photos, OAuth state, credentials,
   and assistant drafts.

**Affected files or subsystems**

- `app/src/main/AndroidManifest.xml`
- `app/src/main/res/xml/`
- app backup-policy instrumentation tests

**Dependencies**

- Android Auto Backup and data-extraction rules

**Estimated effort**

- 2d

**Done when**

- [ ] The installed application participates in Android backup.
- [ ] Both policy formats contain the same narrow database and DataStore
      allowlist.
- [ ] Secure preferences, media, caches, and other files are absent from the
      allowlist for cloud and device transfer.

### Item 2 - Restore-safe local state

**Why**

Restoring the database without excluded private media can leave legitimate
metadata records whose files are unavailable on the new installation.

**What to do**

1. Keep restored Room data authoritative and treat absent imported media or
   transformation-photo files as recoverable missing-media states.
2. Ensure startup, workout guidance, transformation comparison, and backup
   export do not crash when restored media files are absent.
3. Preserve the next manual encrypted restore opportunity rather than deleting
   missing-media records automatically.

**Affected files or subsystems**

- `core:media`
- `feature:workouts`
- `feature:transformation`
- `feature:settings`

**Dependencies**

- Item 1

**Estimated effort**

- 2d

**Done when**

- [ ] Restored records with absent media produce useful empty or recovery
      states rather than crashes or silent deletion.
- [ ] A later encrypted full restore can still reattach the original media.

### Item 3 - Honest recovery guidance

**Why**

Android controls backup timing, quota, transport, and restore eligibility, so
Keepfit must not promise that an uninstall can always be undone.

**What to do**

1. Explain automatic structured-data recovery as device-dependent convenience
   in Data & backup.
2. Keep encrypted export visibly described as the complete database,
   preferences, and private-media backup.
3. Document excluded data and the reconnect path for OpenRouter.

**Affected files or subsystems**

- `feature:settings`
- `docs/user-manual/`
- privacy and architecture documentation

**Dependencies**

- Item 1

**Estimated effort**

- 1d

**Done when**

- [ ] UI and documentation distinguish automatic structured-data recovery from
      complete encrypted export.
- [ ] No wording guarantees a backup or restore.

### Item 4 - Opt-in credential recovery adapter

**Why**

Repeated OAuth connections may create additional provider keys after reinstall,
but credentials must not enter normal Android backup or Keepfit's fitness
archive.

**What to do**

1. Add a focused credential-recovery boundary with a disabled-by-default
   consent preference and an unavailable implementation for devices without
   supported Google services.
2. Integrate Android Block Store using a Keepfit-specific key; enable cloud
   backup only when end-to-end encryption is available.
3. Validate a recovered OpenRouter token before saving it to the Keystore-backed
   credential store; clear invalid recovered bytes and show reconnect guidance.
4. Erase Block Store recovery data when consent is withdrawn or the user
   disconnects.

**Affected files or subsystems**

- `feature:assistant`
- `core:preferences`
- `feature:settings`
- app dependency injection

**Dependencies**

- Google Play services Block Store; existing OpenRouter token validation

**Estimated effort**

- 3d

**Done when**

- [ ] Credential recovery is explicit opt-in and hidden or unavailable safely
      without supported Google services.
- [ ] Normal Android backup and manual fitness backup still contain no token.
- [ ] Missing, unreadable, unavailable, and invalid recovered tokens never
      replace a valid local credential and always permit reconnecting.

### Item 5 - Reinstall and regression evidence

**Why**

Backup behavior varies by device and service, and a recovery feature is useful
only when its privacy boundaries are executable and testable.

**What to do**

1. Add policy tests and fakes for supported, unavailable, invalid, withdrawal,
   and disconnect credential-recovery paths.
2. Exercise `bmgr` backup/restore on the API 36 emulator, including an
   uninstall/reinstall cycle where the transport permits it.
3. Re-run encrypted backup, startup, database, assistant, Settings, lint, and
   APK verification.

**Affected files or subsystems**

- app and feature test suites
- release execution evidence

**Dependencies**

- Items 1-4

**Estimated effort**

- 2d

**Done when**

- [ ] Executable tests prove the allowlist and secret/media exclusions.
- [ ] Emulator backup/restore results and platform limitations are recorded.
- [ ] Existing encrypted backup and offline workflows still pass.
