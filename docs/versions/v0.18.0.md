# Version Spec - v0.18.0 - Validated AI Plan Review

> **Linked initiative:** [Durable Personalized Fitness Companion](../backlog/items/durable-personalized-fitness-companion.md)
> **Status:** Approved and frozen for execution
> **Estimated effort:** 8-12d
> **Risk:** High
> **Prerequisites:** v0.17.0 implementation complete; its connected-device verification remains tracked separately

---

## Sprint Goal

Let a connected person turn onboarding constraints or an explicit Coach request
into a locally validated workout-plan draft, understand it before anything
changes, and apply it only through an unmistakable approval action.

## Delivered Increment

The onboarding AI path opens a focused planning request using the active
profile's saved constraints. Coach can also start the same flow later. The
provider must choose from bounded, supplied offline exercise identifiers;
Keepfit rejects malformed, unknown, duplicate, unsafe, or out-of-scope output.
The existing plan remains untouched while a readable draft is reviewed, and an
approved draft replaces the active weekly plan atomically. Existing manual
schedule and saved-food reviews become accessible through the same explicit
preview-and-approval pattern.

## Work Items

### Item 1 - Strict local plan contract

**Why**

The dormant draft path trusts exercise names and can create invented exercises,
which is incompatible with the audited offline catalogue and approval model.

**What to do**

1. Build a bounded planning context from the active profile's journey answers
   and available offline exercises.
2. Require one structured tool result containing known exercise UUIDs, unique
   weekdays, bounded sets/repetitions, and concise rationale.
3. Validate every field and resolve display names locally before a draft can
   reach UI state.
4. Refuse unsafe planning requests before reserving provider usage.

**Affected files or subsystems**

- `feature:assistant` plan context, contract, validator, repository, fixtures
- `app` profile-aware context adapter

**Dependencies**

- Stable bundled catalogue from v0.14.0
- Progressive journey answers from v0.16.0

**Estimated effort**

- 3d

**Done when**

- [ ] Provider output can reference only supplied active exercise UUIDs.
- [ ] Unknown IDs, repeated days/exercises, invalid targets, and extra fields
      fail closed without changing Room.
- [ ] Unsafe requests fail before credential reservation or network dispatch.

### Item 2 - Atomic approval and recovery

**Why**

A reviewed plan must not erase the current week incrementally or leave partial
templates when validation or storage fails.

**What to do**

1. Revalidate the complete draft against active catalogue records at approval.
2. Apply the weekly plan, templates, exact exercise targets, and assignments in
   one Room transaction owned by the active profile.
3. Preserve the existing active plan until the transaction succeeds.
4. Keep a failed or dismissed draft recoverable for revision or retry without
   silently applying it.

**Affected files or subsystems**

- `app` approval adapter
- `core:database` focused plan transaction APIs if required
- `feature:assistant` ViewModel draft lifecycle

**Dependencies**

- Item 1

**Estimated effort**

- 2d

**Done when**

- [ ] No workout row changes before explicit approval.
- [ ] Approval is all-or-nothing and constrained to the active profile.
- [ ] Exact validated sets, repetitions, exercise order, and weekday order are
      retained after apply.

### Item 3 - Planning and review experience

**Why**

Structured output is only trustworthy when the person can see what will
change, distinguish evidence from suggestion, and back out easily.

**What to do**

1. Route the onboarding AI choice into a focused Coach planning request while
   preserving connect-first disclosure when OpenRouter is unavailable.
2. Add a compact Coach planning action that does not displace the transcript.
3. Present the proposed week as a readable vertical schedule with rationale,
   exercises, targets, revise, dismiss, and explicit apply actions.
4. Surface existing manual weekly-schedule and saved-food review contracts
   through the same observed/current/proposed/reason approval language.

**Affected files or subsystems**

- onboarding-to-Coach navigation state
- `feature:assistant` Compose UI and ViewModel
- Compose behavior and accessibility tests

**Dependencies**

- Items 1-2

**Estimated effort**

- 3d

**Done when**

- [ ] Onboarding can reach AI plan creation without re-entering saved answers.
- [ ] A draft clearly shows every day, exercise, set target, and repetition
      target before approval.
- [ ] Manual schedule/meal reviews remain preview-only until approval.
- [ ] Disconnected, provider-limit, invalid-output, retry, compact-width, and
      200% text states are usable.

### Item 4 - Release verification and guidance

**Why**

This is the first user-visible path that can replace a weekly plan, so safety,
privacy, recovery, and documentation need release-level evidence.

**What to do**

1. Update version metadata, architecture, data-flow boundaries, and user guide.
2. Verify profile isolation, failure rollback, provider privacy preferences,
   restart recovery, and no-change-before-approval behavior.
3. Run focused and broad tests, lint, assembly, package inspection, connected
   UI/Room checks, install, launch, and visual review where a device is present.

**Affected files or subsystems**

- Android version metadata
- architecture and user documentation
- automated and manual verification

**Dependencies**

- Items 1-3

**Estimated effort**

- 2d

**Done when**

- [ ] The UI accurately explains what will change and what data is sent.
- [ ] Unit, Room, migration/regression, Compose, lint, and build checks pass.
- [ ] Device-only gaps are recorded rather than reported as verified.

## Testing Requirements

- [ ] Start with failing contract, validator, provider, approval, ViewModel,
      navigation, and Compose tests.
- [ ] Unit-test unknown UUIDs, duplicates, bounds, unsafe prompts, provider
      failures, retry, dismissal, and no-change-before-approval.
- [ ] Room-test atomic replacement, target retention, rollback, and active-
      profile isolation.
- [ ] Compose-test onboarding entry, complete plan preview, approval wording,
      disconnected state, compact width, and 200% text.
- [ ] Run repository unit tests, relevant connected suites, lint, assembly,
      install/launch when available, and APK version inspection.

## Definition of Done

- [ ] Every work-item checklist is complete.
- [ ] AI planning is optional and offline/manual planning remains complete.
- [ ] Only validated bundled exercise records can enter an AI-created plan.
- [ ] Existing fitness data remains unchanged until explicit approval.
- [ ] Approval is atomic, profile-scoped, recoverable on failure, and visible.
- [ ] Safety, privacy, accessibility, regression, and build checks pass.
