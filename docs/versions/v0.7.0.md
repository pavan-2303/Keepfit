> **Linked initiative:** [Practical Fitness Journey and Optional AI Coach](../backlog/items/practical-fitness-journey-and-ai-coach.md)
> **Status:** In Progress - frozen when execution began on 2026-09-13
> **Estimated effort:** 8-12d
> **Risk:** High

## Sprint Goal

Make the exercise library useful before personal setup and validate animated
online discovery without making remote content authoritative or required.

## Delivered Increment

The user can browse 40 Keepfit-authored exercise guides offline, filter them by
name, movement area, and equipment, and explicitly add a guide to the personal
library. A separate live, view-only ExerciseDB prototype searches current
provider data and displays attributed animated demonstrations when available.

## Behavioral Contract

- The catalogue has three visibly distinct sources: personal library, Keepfit
  offline guide, and live ExerciseDB demos.
- The offline guide contains exactly 40 internally authored definitions across
  bodyweight, dumbbell, resistance-band, and gym equipment.
- Offline definitions are deterministic application content, not Room rows.
  They remain searchable without internet access or prior setup.
- Adding an offline guide is explicit and creates an ordinary editable local
  `Exercise`. An active exercise with the same case-insensitive name is not
  duplicated.
- Existing starter-plan keys and ordering remain stable. The expanded guide may
  be used by starter planning without changing existing persisted plans.
- Live search is user-initiated and sends only entered search and selected
  catalogue filters. It never sends profile, plan, workout, nutrition,
  transformation, identifier, note, or media data.
- `ExerciseCatalogProvider` owns provider-independent queries, results, and
  failure categories. The AscendAPI adapter owns HTTP and response mapping.
- Live results are held only in screen/ViewModel memory. They are never written
  to Room, app-private storage, DataStore, backup archives, or logs.
- The prototype exposes no remote `Add to library` action because commercial,
  attribution, caching, and persistence rights have not been confirmed in
  writing.
- GIF requests disable Coil memory and disk caches. A fresh provider response
  supplies the current media URL; missing or invalid media shows instructions
  instead of a broken player.
- Search handles loading, empty, offline, timeout, malformed-response, and
  provider-error states with a retry path that requires another user action.
- Provider attribution and the view-only/private-prototype boundary remain
  visible wherever live results or media are displayed.
- No Room migration or backup-format change is required because remote content
  is transient and offline definitions are bundled code content.
- Existing local exercise creation, media import, templates, plans, sessions,
  history, backup, and restore continue working when the network or provider is
  unavailable.

## Work Items

### Item 1 - Expand and govern the owned offline guide

**Why**

The current 16 original exercises support starter planning but are not a
browsable first-launch library and do not cover enough common alternatives.

**What to do**

1. Expand the stable offline definitions from 16 to 40 with concise original
   instructions and balanced equipment coverage.
2. Add deterministic search/filter rules and an idempotent add-to-library path.
3. Create an asset and content rights register for every shipped source.

**Affected files or subsystems**

- `feature:workouts` planning and catalogue packages
- Workout repository/ViewModel
- `docs/references`

**Dependencies**

- Existing starter catalogue and exercise persistence

**Estimated effort**

- 3d

**Done when**

- [ ] Forty owned guides are searchable offline and existing keys remain stable.
- [ ] Adding a guide is explicit, editable, and duplicate-safe.
- [ ] Rights and media status are documented for each content source.

### Item 2 - Add a transient provider adapter

**Why**

Online discovery needs stable app-facing models and testable failures without
coupling workout records to one provider or storing restricted data.

**What to do**

1. Define catalogue query, item, response, and failure contracts.
2. Implement the keyless ExerciseDB V1 adapter with bounded timeouts, safe URL
   construction, strict response mapping, and no persistent cache.
3. Add recorded-fixture tests for mapping, filters, malformed rows, rotating
   media URLs, offline, timeout, and provider failures.

**Affected files or subsystems**

- `feature:workouts` catalogue package
- App dependency wiring
- Version catalogue and workout dependencies

**Dependencies**

- AscendAPI ExerciseDB V1 free hosted endpoint

**Estimated effort**

- 3d

**Done when**

- [ ] Provider contracts are independent, deterministic, and fully fakeable.
- [ ] Failures preserve the last query and never mutate local fitness data.
- [ ] Automated tests make no live network calls.

### Item 3 - Build the source-aware catalogue experience

**Why**

Users must immediately understand which content is theirs, which works
offline, and which is a transient online demonstration.

**What to do**

1. Add the exercise-source provenance rail and source-specific search/filter
   states to the Exercises tab.
2. Add offline detail and explicit add-to-library flows.
3. Add live search, attributed detail, GIF playback, missing-media, retry, and
   view-only disclosures with caching disabled.

**Affected files or subsystems**

- Workout Compose UI and ViewModel
- Coil image loading

**Dependencies**

- Items 1-2

**Estimated effort**

- 3d

**Done when**

- [ ] Personal, offline, and live sources cannot be confused.
- [ ] Core offline planning and exercise management work with the provider off.
- [ ] Animated demonstrations are visible only after a deliberate live action.

### Item 4 - Integrate, document, and verify

**Why**

The prototype introduces network and third-party content risk and must ship
with explicit privacy, licensing, reliability, and test evidence.

**What to do**

1. Update version metadata, architecture, README, privacy/user guidance, and
   the initiative state.
2. Add unit and Compose tests for source switching, filters, addition, animated
   detail, and every failure state.
3. Run broad build gates and manually verify offline and live flows on a
   current emulator, including an upgrade from existing data.

**Affected files or subsystems**

- App metadata, tests, and documentation

**Dependencies**

- Items 1-3

**Estimated effort**

- 2d

**Done when**

- [ ] App reports version 0.7.0 and documentation matches shipped behavior.
- [ ] Verification proves remote data is transient and offline use remains complete.
