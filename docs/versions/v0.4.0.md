# Version Spec - v0.4.0 - Low-Friction Workout Execution

> **Linked initiative:** [Practical Fitness Journey and Optional AI Coach](../backlog/items/practical-fitness-journey-and-ai-coach.md)
> **Status:** In Progress
> **Estimated effort:** 8-12d
> **Risk:** High
> **Prerequisites:** v0.3.0 Decisive Today, current active-workout logging,
> workout history, and configurable local rest timer

---

## Sprint Goal

Make an active workout fast and resilient enough for real gym use: prior values
are ready to reuse, each completed set starts the configured rest timer,
in-session changes are safe, completion feedback is optional, and progression
advice is local, bounded, and explained.

## Delivered Increment

A user can return to an interrupted active session, log or repeat a set with
minimal typing, see target and progress context, switch to a minimum session or
substitute an untouched exercise, and complete with optional energy and
difficulty feedback. Keepfit suggests either repeating the prior performance or
one small next-step increase using a deterministic rule over completed history.

## Scope Boundaries

- Keep execution and progression fully offline and deterministic.
- Store active-session state in Room; use saved UI state only for transient
  timer and dialog state.
- Never rewrite the reusable template or dated occurrence while adapting an
  already-started session.
- Allow substitution only before sets are logged for that exercise and reject
  duplicate exercises in one session.
- Allow conversion to a minimum session only when exercises being removed have
  no logged sets; retain the first two exercises in execution order.
- Keep energy and difficulty feedback optional and use a bounded 1-5 scale.
- Do not add RPE per set, supersets, plate calculators, automatic template
  progression, cloud sync, or AI advice.

## Deterministic Progression Contract

For the most recent completed performance of an exercise:

1. If there is no completed set history, show no progression suggestion.
2. If the completed set count or repetitions do not meet the current target,
   suggest repeating the previous values.
3. If every required set reaches the parsed upper repetition target at a
   positive weight, suggest a 2.5% increase rounded to the nearest 0.5 kg, with
   the increase clamped from 0.5 kg through 2.5 kg.
4. If the same condition is met at zero weight, suggest one additional
   repetition, capped at two above the parsed target.
5. If the repetition target cannot be parsed, suggest repeating the prior
   values and explain that the target is not numeric.

Suggestions are display-only. The user edits or accepts the values for each set;
Keepfit never modifies templates or inserts future sets automatically.

## Work Items

### Item 1 - Persist resilient execution context

**Why**

An active session currently survives in Room, but exercise targets and
completion feedback are not durable session facts.

**What to do**

1. Snapshot nullable target sets and reps onto new exercise logs.
2. Add a canonical session variant plus nullable 1-5 energy and difficulty
   feedback to workout sessions.
3. Add transactional DAO commands for append-set, repeat-previous-set,
   untouched-exercise substitution, minimum-session conversion, and completion.
4. Increment Room from schema 7 to 8, export the schema, add migration tests,
   and prove backup restore retains the new fields.

**Affected files or subsystems**

- `core:database` workout entities, DAO, migration, and schema export
- `feature:settings` encrypted backup verification

**Dependencies**

- Existing workout session, exercise log, and set log tables

**Estimated effort**

- 3d

**Done when**

- [ ] Existing schema-7 sessions migrate without losing logs or completion.
- [ ] New sessions retain targets, variant, and optional feedback through
  process restart and backup restore.
- [ ] Concurrent or repeated commands cannot create invalid set positions,
  duplicate exercises, or silently delete logged work.

### Item 2 - Add deterministic set and progression rules

**Why**

Useful defaults reduce typing, while an explicit local rule keeps progression
understandable and reversible.

**What to do**

1. Load the ordered sets from the most recent completed session for each active
   exercise.
2. Prefill the next editable inputs from the corresponding prior set, falling
   back to the final prior set.
3. Add one-tap repeat of that prior set.
4. Implement the frozen progression contract as a pure tested rule and expose
   its proposed values and explanation with the active exercise.
5. Start the configured rest timer only after a set write succeeds.

**Affected files or subsystems**

- `feature:workouts` execution models, rules, repository, and ViewModel
- `core:preferences` existing rest-timer setting consumption

**Dependencies**

- Item 1

**Estimated effort**

- 3d

**Done when**

- [ ] Previous-set defaults and repeat behavior are deterministic by set
  position.
- [ ] Suggestions follow the bounded contract and state why weight, reps, or no
  change is proposed.
- [ ] A successful set starts the configured timer; an invalid or failed set
  does not.

### Item 3 - Build the focused active-workout flow

**Why**

The current form works but requires too much scanning and typing during a real
session.

**What to do**

1. Recompose the screen around a compact session header, visible rest timer,
   exercise progress, target context, and large set actions.
2. Prefill editable reps and weight, provide repeat-previous-set, and retain
   useful values as the next set advances.
3. Add review dialogs for substitution and conversion to a minimum session.
4. Add an optional completion sheet for energy and difficulty, including a
   clear complete-without-feedback path.
5. Restore the active session after recreation and preserve transient timer and
   dialog state where Android saved state permits.

**Affected files or subsystems**

- `feature:workouts` active-workout Compose UI and ViewModel
- `app` navigation behavior only if required for restoration

**Dependencies**

- Items 1-2

**Estimated effort**

- 3d

**Done when**

- [ ] A normal set can be logged or repeated with one primary action and no
  re-entry of unchanged prior values.
- [ ] Minimum and substitution previews protect logged work and reusable plans.
- [ ] Completion works with or without feedback and returns to durable history.
- [ ] Loading, empty-history, timer, validation, large-text, and recreation
  states remain usable.

### Item 4 - Integrate, document, and verify

**Why**

Execution changes touch history, migration, backup, and the highest-frequency
screen, so they require release-level verification.

**What to do**

1. Update the application to version `0.4.0` and version code `4`.
2. Update current architecture, data-model, README, and workout user guidance.
3. Run focused red-green tests, broad unit tests, lint, build, migration,
   backup, repository, Compose, process-recreation, and manual emulator checks.

**Affected files or subsystems**

- application metadata, documentation lifecycle, and verification fixtures

**Dependencies**

- Items 1-3

**Estimated effort**

- 1-3d

## Testing Requirements

- [ ] Unit tests cover target parsing, previous-set selection, repeat behavior,
  progression bounds, bodyweight progression, and repeat/no-history outcomes.
- [ ] Repository and DAO tests cover partial sessions, successful and rejected
  substitutions, minimum conversion, set ordering, feedback, and restoration.
- [ ] Room migration 7-to-8 and backup instrumentation preserve legacy and new
  session fields.
- [ ] Compose tests cover prefilled values, repeat, automatic timer callback,
  adaptations, completion feedback, and skip-feedback completion.
- [ ] Recreation coverage proves persisted sets and active-session adaptations
  are recovered without duplication.
- [ ] `testDebugUnitTest`, `lintDebug`, `assembleDebug`, and relevant connected
  suites pass on the available Android emulator or device.

## Definition of Done

- [ ] Every work-item checklist is complete.
- [ ] The delivered increment is usable, not placeholder-only.
- [ ] Required tests and verification steps pass.
- [ ] No template, occurrence, or completed history is silently rewritten.
- [ ] Follow-up work is captured separately rather than left implicit.
