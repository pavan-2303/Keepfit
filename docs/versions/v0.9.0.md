# Version Spec - v0.9.0 - Bounded Coaching Workflows

> **Linked initiative:** [Practical Fitness Journey and Optional AI Coach](../backlog/items/practical-fitness-journey-and-ai-coach.md)
> **Status:** In Progress - frozen when execution began on 2026-09-13
> **Estimated effort:** 8-12d
> **Risk:** High
> **Prerequisites:** v0.5.0 weekly review and v0.8.0 private OpenRouter access complete

---

## Sprint Goal

Turn the optional assistant from free-form text generation into bounded,
locally validated coaching proposals that show their evidence and cannot change
fitness data until the user explicitly approves them.

## Delivered Increment

The user can request a weekly summary, schedule change, shorter workout,
exercise substitution, existing-food meal, or weekly-plan proposal. OpenRouter
must return a required tool call. Keepfit resolves only aliases it supplied,
validates the complete proposal locally, displays observed/current/proposed/
reason fields, and applies a supported mutation only after approval.

## Behavioral Contract

- Coaching intent and proposal models are provider independent. OpenRouter owns
  transport and credentials only.
- Structured actions force one named function call with parallel calls disabled.
- Unknown tools, unknown or additional fields, missing fields, excessive
  values, unresolved aliases, duplicate days, invalid dates, and malformed JSON
  fail closed.
- Prompts use bounded display aliases. Room identifiers, paths, notes, photos,
  profile identity, birth date, height, weight, BMI, and measurements are never
  sent.
- A proposal contains observed evidence, current state, proposed state, and a
  concise reason. Model text is not treated as a command.
- Preview and edit do not write fitness data. Approval invokes one focused,
  locally checked command; dismissal writes nothing.
- Pending input and the latest validated proposal survive recreation locally
  and remain outside Keepfit backup exports.
- A local safety gate refuses diagnosis, injury rehabilitation, medication,
  extreme-deficit, eating-disorder, and unsafe progression requests before
  dispatch, so refusals do not consume the daily allowance.
- Quota, authentication, malformed response, safety, and connectivity failures
  preserve the typed request and any existing proposal.
- Disabling or disconnecting the coach leaves deterministic planning, Today,
  workout, nutrition, and weekly-review workflows unchanged.
- The fixed evaluation gate is 100% local validation and privacy-fixture pass,
  100% safety-refusal pass, at least 90% valid tool calls, and at least 85% task
  completion for the named model. Live-model results are recorded separately
  from deterministic fixture results.

## Work Items

### Item 1 - Provider-independent bounded contracts

1. Add coaching intents, sanitized alias catalogues, proposal operations, tool
   schemas, response parsing, and exhaustive local validation.
2. Extend the OpenRouter adapter to force the requested tool, disable parallel
   tool calls, retain privacy routing, and return raw tool arguments only.
3. Cover all supported intents with recorded provider fixtures and malicious
   input cases.

### Item 2 - Safe context, safety, and local recovery

1. Build compact context from existing templates, today's workout, exercises,
   foods, and weekly signals without provider-visible identifiers or notes.
2. Refuse high-risk medical, rehabilitation, medication, extreme-deficit, and
   unsafe progression requests locally with clear general guidance.
3. Persist the typed request and latest validated proposal in a dedicated
   local-only store excluded from backup.

### Item 3 - Review and approval experience

1. Replace generic assistant shortcuts with small task choices and a single
   focused request field.
2. Present observed/current/proposed/reason and operation-specific details.
3. Support edit, approve, and dismiss while preserving the proposal on apply
   failure and never writing during preview.

### Item 4 - Evaluation, documentation, and release artifact

1. Add at least 50 stable evaluation cases covering normal, boundary, safety,
   injection, malformed, quota, and provider conditions.
2. Run focused, repository-wide, connected-device, persistence, and APK checks.
3. Update architecture, data model, privacy disclosure, user manual, roadmap,
   version metadata, and the next journey-UX slice.

## Definition of Done

- [ ] Every work-item checklist is complete.
- [ ] All supported coaching actions require valid tool output and explicit
  approval before mutation.
- [ ] Safety and privacy gates have deterministic evidence.
- [ ] The named model meets the declared live evaluation threshold, or the
  version remains pre-beta with the unmet gate stated explicitly.
- [ ] Existing offline workflows remain runnable with AI disabled.
- [ ] The next approved product theme is journey and interface reorganization.
