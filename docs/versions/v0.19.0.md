# Version Spec - v0.19.0 - Training Field Guide Polish

> **Linked initiative:** [Durable Personalized Fitness Companion](../backlog/items/durable-personalized-fitness-companion.md)
> **Status:** Approved and frozen for execution
> **Estimated effort:** 8-12d
> **Risk:** Medium
> **Prerequisites:** [v0.18.0 complete](../done/versions/v0.18.0.md)

---

## Sprint Goal

Give Keepfit a recognizable, disciplined visual identity and purposeful motion
that make daily training feel clearer and more rewarding without adding noisy
gamification, remote assets, or accessibility regressions.

## Delivered Increment

The shell and primary Today, Plan, Coach, workout-completion, and Settings
touchpoints share one training-field-guide hierarchy, consistent surfaces, and
plain-language status treatment. Navigation, state changes, disclosure, and
completion use restrained native motion; confirmed actions may use subtle
haptics. Motion follows the user's reduced-motion choice, large text remains
usable, and the app stays responsive on the supported emulator profile.

## Work Items

### Item 1 - Field-guide design system

**Why**

The app is now usable but still relies on generic Material defaults and
screen-local styling, making dense features feel unrelated.

**What to do**

1. Refine color, typography, shapes, elevation, spacing, and icon treatment
   around the existing field green and action orange identity.
2. Add focused shared Compose primitives for section headings, hero actions,
   status marks, and compact supporting surfaces.
3. Keep the system offline, code-native, contrast-safe, and legible at 200%
   text without adding remote fonts or decorative media.

**Affected files or subsystems**

- `core:designsystem`
- shared Compose call sites

**Dependencies**

- Existing five-destination information architecture

**Estimated effort**

- 2d

**Done when**

- [ ] Shared tokens and primitives encode a consistent hierarchy.
- [ ] The identity is recognizable without gradients, remote art, or a grid of
      equal rounded cards.
- [ ] Core components remain usable at compact width and 200% text.

### Item 2 - Core journey application

**Why**

Visual consistency matters most where a person decides what to do, performs a
workout, checks progress, or asks Coach for help.

**What to do**

1. Apply the new hierarchy to the app shell and decisive Today state.
2. Align Plan, Coach, Settings, and completion touchpoints with the same
   section, status, and action language.
3. Remove decorative or oversized treatment that competes with primary tasks.

**Affected files or subsystems**

- `app` home shell and Today composition
- `feature:workouts`, `feature:assistant`, and `feature:settings` UI

**Dependencies**

- Item 1

**Estimated effort**

- 3d

**Done when**

- [ ] Primary actions and current state are visually unambiguous.
- [ ] Coach responses and the workout workflow keep useful content above
      configuration or decoration.
- [ ] Sentence case, spacing, and component roles are consistent.

### Item 3 - Purposeful motion and confirmation

**Why**

Motion should explain a state change or confirm work, not make a fitness log
feel busy or slow.

**What to do**

1. Animate destination and state changes with short, content-preserving native
   transitions.
2. Add a restrained completion treatment and haptic confirmation only after a
   user-confirmed action succeeds.
3. Respect the system animation scale and an explicit local reduced-motion
   preference.

**Affected files or subsystems**

- `core:designsystem` motion policy
- `core:preferences` accessibility preference
- app navigation and focused workout actions

**Dependencies**

- Items 1-2

**Estimated effort**

- 2d

**Done when**

- [ ] Motion communicates navigation, progress, disclosure, or completion.
- [ ] Reduced motion removes nonessential transitions without hiding state.
- [ ] Haptics never fire for loading, failure, or passive screen entry.

### Item 4 - Accessibility and performance closeout

**Why**

Polish is not complete if it reduces contrast, breaks large text, or makes
daily screens slower.

**What to do**

1. Test compact width, 200% text, semantic labels, contrast, and reduced
   motion across the changed journeys.
2. Run unit, Compose, lint, assembly, connected regression, install, launch,
   startup, and frame-timing checks where the emulator is available.
3. Update user and architecture guidance and package metadata.

**Affected files or subsystems**

- changed Compose tests
- documentation and Android metadata

**Dependencies**

- Items 1-3

**Estimated effort**

- 2d

**Done when**

- [ ] Accessibility, lint, build, and connected tests pass.
- [ ] Startup and frame evidence show no material regression.
- [ ] The installed v0.19.0 package passes a phone-width visual walkthrough.
