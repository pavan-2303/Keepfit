# Version Spec - v0.12.0 - Isolated Local Profiles

> **Linked initiative:** [Durable Personalized Fitness Companion](../backlog/items/durable-personalized-fitness-companion.md)
> **Status:** Approved and frozen for execution
> **Estimated effort:** 10-12d
> **Risk:** High
> **Prerequisites:** [v0.11.0 complete](../done/versions/v0.11.0.md)

---

## Sprint Goal

Let several people use one Keepfit installation while every personal plan,
log, goal, review, transformation record, journey answer, and preference stays
within the selected local profile.

## Delivered Increment

A user can open the avatar menu, add a local profile, switch immediately, edit
its basic details, or archive an unused profile. Exercise and food reference
libraries remain shared, but all personal workflows react to the active
profile and cannot read or mutate another profile's records. Existing installs
migrate every current personal record to the existing profile and retain it as
the active profile. Encrypted backup continues to include all profiles.

## Work Items

### Item 1 - Profile-owned Room schema and migration

**Why**

Several root tables are currently global, so switching only the displayed name
would mix plans and history.

**What to do**

1. Add archive state to body profiles and profile ownership to workout
   templates, weekly plans, workout occurrences, workout sessions, saved
   meals, diary entries, meal-quality check-ins, and weekly-review outcomes.
2. Keep exercises, exercise media, and foods as device-wide reference
   libraries; children inherit ownership from their personal root record.
3. Migrate every existing personal row to the existing profile in one Room
   migration and rebuild profile-sensitive unique indexes.

**Affected files or subsystems**

- `core:database` entities, DAOs, schema, migrations, and migration tests
- repository construction sites and fixtures

**Dependencies**

- Existing body profile identifiers

**Estimated effort**

- 4d

**Done when**

- [ ] Room schema version increments and its schema is exported.
- [ ] Migration assigns all prior personal roots to the existing profile
      without changing shared exercise or food records.
- [ ] Profile-specific uniqueness and foreign-key constraints are executable.

### Item 2 - Active-profile state and preferences

**Why**

Every feature needs one observable profile identity, including after process
restart and Android restore.

**What to do**

1. Store the active profile identifier in the allowlisted DataStore and repair
   a missing or archived selection deterministically.
2. Expose a focused active-profile boundary from `core:preferences` for feature
   repositories.
3. Namespace profile-owned settings while retaining device-level credential
   recovery and integration state separately; seed the original profile from
   existing settings.

**Affected files or subsystems**

- `core:preferences`
- app profile repository and startup state
- reminder coordination

**Dependencies**

- Item 1

**Estimated effort**

- 2d

**Done when**

- [ ] Active profile survives restart and invalid selections fall back safely.
- [ ] Switching profiles switches profile-owned settings without copying one
      person's later edits to another.
- [ ] Credential recovery remains an explicit device-level setting.

### Item 3 - Repository isolation

**Why**

UI filtering is insufficient; every read and write must be scoped at the DAO
or transactional repository boundary.

**What to do**

1. Scope workout planning, occurrences, active sessions, history, records,
   nutrition diaries and saved meals, weekly reviews, goals, journeys,
   measurements, transformations, and assistant summaries to the active
   profile.
2. Require the active profile identifier on personal mutations and reject
   cross-profile identifiers inside transactions.
3. Keep shared exercise and food catalogue behavior unchanged.

**Affected files or subsystems**

- `feature:workouts`
- `feature:nutrition`
- `feature:review`
- `feature:settings`
- `feature:transformation`
- app assistant-summary coordination

**Dependencies**

- Items 1-2

**Estimated effort**

- 3d

**Done when**

- [ ] Each personal repository has cross-profile read and mutation tests.
- [ ] Switching profiles updates existing screen state without app restart.
- [ ] Shared exercise and food records remain available to every profile.

### Item 4 - Compact profile management

**Why**

Profile switching should feel like an account switcher, not another large
Settings form.

**What to do**

1. Replace the single profile/settings icon with a compact initial avatar that
   opens the profile menu.
2. List active profiles, mark the current one, and provide add, edit, archive,
   and Settings actions without social or account language.
3. Prevent archiving the final profile and move away from an archived active
   profile atomically from the user's perspective.

**Affected files or subsystems**

- app profile ViewModel and Compose shell
- Coach header and Settings entry
- profile UI tests

**Dependencies**

- Items 1-3

**Estimated effort**

- 2d

**Done when**

- [ ] Add, switch, edit, and archive are usable from the app bar.
- [ ] The final active profile cannot be archived.
- [ ] Compact width, large text, and accessibility labels remain usable.

### Item 5 - Backup and regression evidence

**Why**

Profile isolation changes almost every authoritative record boundary and must
not weaken recovery.

**What to do**

1. Prove encrypted export/restore includes all profiles and restores the active
   profile plus namespaced settings.
2. Add DAO/repository tests that use colliding dates and active states across
   two profiles.
3. Run migration, connected UI, unit, lint, APK, upgrade-install, and fresh
   install checks.

**Affected files or subsystems**

- backup tests and documentation
- release execution evidence

**Dependencies**

- Items 1-4

**Estimated effort**

- 1d

**Done when**

- [ ] Backup round trips preserve every profile and its personal records.
- [ ] Cross-profile leakage tests fail before implementation and pass after it.
- [ ] Upgrade and fresh-install workflows remain runnable.

## Definition of Done

- [ ] Every work-item checklist is complete.
- [ ] Existing user data migrates to the original profile without loss.
- [ ] All personal reads and writes are scoped below the UI boundary.
- [ ] Exercise and food catalogues remain intentionally shared.
- [ ] Active profile and profile-owned preferences survive restart and backup.
- [ ] Add, switch, edit, and archive are practical from one compact menu.
- [ ] The final profile cannot be archived.
- [ ] Encrypted backup includes all profiles and remains restorable.
- [ ] Required tests, lint, upgrade checks, and APK assembly pass.
