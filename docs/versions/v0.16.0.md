# Version Spec - v0.16.0 - Progressive Onboarding and Manual Planning

> **Linked initiative:** [Durable Personalized Fitness Companion](../backlog/items/durable-personalized-fitness-companion.md)
> **Status:** Approved and frozen for execution
> **Estimated effort:** 8-12d
> **Risk:** Medium
> **Prerequisites:** [v0.15.0 complete](../done/versions/v0.15.0.md)

---

## Sprint Goal

Turn first run into a purposeful, resumable fitness intake that records useful
baseline context and ends in a real planning choice without requiring an
account, network connection, or AI provider.

## Delivered Increment

A new user moves through short profile and training questions, sees age and BMI
context calculated locally when enough optional data is supplied, and chooses
one of three honest next steps: preview an offline starter week, build manually
in Plan, or open the existing query-only Coach. The survey remains editable,
skippable where inputs are optional, profile-scoped, and usable with large text
and the keyboard.

## Work Items

### Item 1 - Useful baseline profile intake

**Why**

The current name-and-height form does not collect enough context to make later
planning feel personal or show why optional body data is useful.

**What to do**

1. Split first-run profile setup into focused identity and baseline steps.
2. Collect optional birth date, height, and starting weight with plain-language
   explanations, skip behavior, validation, and edit-later copy.
3. Persist birth date on the profile and starting weight as the first dated body
   measurement, using existing schema fields and profile ownership.
4. Derive visible age and BMI locally without collecting gender or calculation
   sex, since neither changes BMI or this version's planner.

**Affected files or subsystems**

- `app` profile setup, validation, repository, and tests
- existing Room profile and transformation tables
- getting-started and data-model documentation

**Dependencies**

- v0.12.0 profile isolation

**Estimated effort**

- 3d

**Done when**

- [ ] First run presents one meaningful profile decision at a time with clear
      progress, back, skip, and edit-later behavior.
- [ ] Valid birth date and height persist on the active profile and valid
      starting weight creates exactly one profile-owned body measurement.
- [ ] Age and BMI appear only when their source values are available and are
      described as general context rather than medical advice.
- [ ] No new schema, account, network request, or purposeless sensitive field is
      introduced.

### Item 2 - Practical training preference survey

**Why**

The existing starter-plan form contains the right broad inputs but presents
them as a long sequence of similarly weighted controls, including an
overwhelming exercise-avoidance list.

**What to do**

1. Restyle the survey as compact notebook-like steps with a persistent progress
   trail, clear question hierarchy, and anchored navigation.
2. Keep goal, experience, availability, duration, equipment, movement
   constraints, and nutrition depth profile-scoped and editable.
3. Make movement constraints searchable and selectively expandable so the
   bundled catalogue does not dominate the page.
4. Preserve deterministic offline starter-plan generation and existing saved
   survey values.

**Affected files or subsystems**

- `feature:workouts` starter-plan UI and state
- journey preferences and nutrition settings
- Compose and ViewModel tests

**Dependencies**

- Item 1
- v0.14.0 bundled catalogue

**Estimated effort**

- 3d

**Done when**

- [ ] Every approved planning input remains available without a dense or
      unbounded control dump.
- [ ] Previously selected constraints are visible even when the catalogue list
      is collapsed or filtered.
- [ ] Survey choices survive navigation and continue to generate the same safe,
      deterministic offline week.
- [ ] Compact width, keyboard use, and 200% text remain usable.

### Item 3 - Honest planning route chooser

**Why**

Automatically pushing every user into a generated review ignores people who
already know their routine and overstates what the current query-only Coach can
do.

**What to do**

1. End the intake with a concise comparison of offline starter, manual Plan,
   and Coach query paths.
2. Route offline users to the existing editable preview, manual users directly
   to Plan, and connected or disconnected AI users to Coach without claiming a
   structured plan will be applied.
3. Keep AI optional and show that provider connection is required only after
   the person deliberately chooses Coach.

**Affected files or subsystems**

- `feature:workouts` route choice UI
- `app` navigation shell
- navigation and Compose tests

**Dependencies**

- Item 2
- existing v0.8.0 query-only Coach connection

**Estimated effort**

- 2d

**Done when**

- [ ] Each of the three choices reaches a useful existing destination.
- [ ] Manual planning and offline planning work with no provider connection.
- [ ] Coach copy remains query-only and does not imply v0.18.0 AI plan
      validation or mutation exists.

### Item 4 - Release verification and guidance

**Why**

First run is a critical path and must remain reliable across accessibility,
offline, profile, backup, and upgrade scenarios.

**What to do**

1. Update app version metadata, architecture notes, and user guidance.
2. Verify profile isolation, starting-measurement ownership, existing-user
   startup, offline completion, and all planning routes.
3. Run focused tests, the broader suite, lint, debug assembly, and installed
   phone/emulator smoke checks.

**Affected files or subsystems**

- Android version metadata
- repository and user documentation
- automated and manual verification

**Dependencies**

- Items 1-3

**Estimated effort**

- 2d

**Done when**

- [ ] Existing profiles bypass first-run onboarding and retain their data.
- [ ] Automated tests, lint, debug build, install, launch, offline, compact
      width, and large-text checks pass.
- [ ] Documentation accurately distinguishes local starter planning, manual
      planning, query-only Coach, and future AI-generated planning.

## Testing Requirements

- [ ] Start with failing validation, repository, BMI/age, survey-state, route
      choice, and Compose behavior tests.
- [ ] Unit-test optional input validation, local derivation, exact first
      measurement creation, omission behavior, and existing-profile editing.
- [ ] Compose-test progressive navigation, back and skip behavior, filtered
      constraints, route choices, compact width, keyboard, and 200% text.
- [ ] Device-test profile ownership and first measurement through Room.
- [ ] Run all unit tests, relevant connected suites, lint, debug assembly,
      clean install, offline launch, and package-version checks.

## Definition of Done

- [ ] Every work-item checklist is complete.
- [ ] First run records useful optional baseline and training context.
- [ ] Offline, manual, and query-only Coach exits are real and accurately named.
- [ ] No schema change, backend, provider dependency, or unnecessary sensitive
      field is added.
- [ ] Existing profile and starter-plan behavior remains compatible.
- [ ] Accessibility, regression, install, offline, and APK checks pass.
